﻿# ESK-LAB-08 — Architecture and Scope

Status: DESIGN BASELINE RECORDED; IMPLEMENTATION AND VERIFICATION PENDING.

## Purpose
Independent Go and PostgreSQL backend demonstration using synthetic
product inventory and reservations. No production or financial claims.

## Architecture
HTTP client -> Go net/http handlers -> reservation service -> pgx -> PostgreSQL.

Handlers validate requests and map service errors to HTTP responses.
The service owns transaction boundaries and business invariants.
PostgreSQL owns durable inventory, reservations and idempotency records.

## Data model
- products: synthetic identifier, SKU, initial quantity, available quantity.
- reservations: identifier, product identifier, positive quantity, status.
- idempotency_requests: unique operation/key, request fingerprint,
  stored HTTP status and response.

Database constraints enforce valid quantities and reservation states.
Foreign keys preserve references.

## Transaction rules
Reservation creation atomically claims an idempotency key, locks the
product row with SELECT FOR UPDATE, checks availability, writes the
reservation, updates stock and stores the successful response.
All changes commit together or roll back together.

Concurrent requests using the same key must resolve to one committed
operation. A different request fingerprint with that key returns conflict.
Only committed successful creation responses are retained for replay;
failed attempts may be retried.

Cancellation locks the reservation and then the product in a consistent
order. Only an active reservation returns stock. Repeated cancellation
does not return additional units.

For each product:
available quantity + total active reserved quantity = initial quantity.

No replenishment, expiration, deletion or multi-product reservations
are included in the initial scope.

## HTTP scope
- GET /healthz: process health.
- GET /readyz: bounded database readiness check.
- GET /products/{id}: synthetic product availability.
- POST /reservations: requires an idempotency key.
- GET /reservations/{id}: reservation status.
- POST /reservations/{id}/cancel: repeat-safe cancellation.

Bounded request bodies, parameterized SQL, context deadlines and
controlled error responses are required. No raw database errors or
credentials in client responses or public evidence.

## Isolation and cost
Local Windows and an explicitly isolated Docker project.
CPU only. No paid infrastructure or APIs.
G1 must verify Docker context, versions, resources, existing names,
ports and mounts before containers are created.
Bind any published ports to loopback only.
No production access, global Docker cleanup or shared-resource removal.
